# Proxy 独立刷新与 MCP 协议兼容改造方案

状态：**Implemented，最终平台结果以对应提交 CI 为准**。日期：2026-10-19。运行时代码、独立后端、协议恢复及迁移已实施；实际断言和测量见 [实施与验证记录](implementation-results.md)。

调研基线：main 的 [32cbd9fe11108f9f897ae1ef1cabbc94b10d1b51](https://github.com/fredgnr/gopls-mcp-proxy/commit/32cbd9fe11108f9f897ae1ef1cabbc94b10d1b51)，tree 为 c011e038126bc7487716ba83b1f3dcf30d6a74ed。

## 目标

由 proxy 独立发现配置范围内的输入变化，通过受控替换 gopls 进程完成刷新。普通调用使用通用 MCP 消息中继，保持原生方法名、工具名称、参数、描述、schema、结果和错误；proxy 不维护 gopls 工具白名单，不调用特定 reload 命令，不依据工具业务含义决定刷新或重试。

正确性必须用一个“仅在启动时读取输入、运行期间完全不会刷新”的受控后端证明。真实 gopls 测试验证互通，不承担证明 proxy 独立刷新的唯一责任。

## 已确定的设计方向

1. **刷新由 proxy 负责。** 默认对工作目录和显式监测根内的常规输入文件计算内容指纹，包括已有 .go 文件的内容。
2. **消息与业务解耦。** 直接中继原始 JSON；只读取通用 envelope 和已支持协议的生命周期字段，必要的 ID 关联改写有明确范围。
3. **同版本端到端优先。** 分别验证具体 MCP 修订；不暗中进行旧协议与现代协议的语义转换。
4. **刷新等待有上限。** 暂停新普通请求，但保持已派发操作所需的响应、取消等控制消息通行；长期订阅不阻止刷新。
5. **已派发业务请求不自动重放。** 超时、崩溃、过期结果均不能成为再次执行原业务调用的依据；已定义并验收的协议初始化/状态重建使用独立恢复白名单。
6. **正常透传与刷新恢复分别承诺。** 标准初始化和明确支持的配置可重建；未知句柄、任务执行状态和不透明续传状态不保证跨进程有效。
7. **无法恢复时显式重连。** 清理已失效后端并要求客户端重建连接，不继续提供已知过期服务。

## 兼容性的含义

| 维度 | 本方案目标 |
|---|---|
| 工具调用接口 | 稳定代次内与原生 MCP 接口一致，不增加工具前缀或重新定义参数 |
| 后端启动 | 采用“proxy 选项 -- 原始程序 原始参数”的明确边界；分隔符之后的参数不解析、不重排 |
| 协议 | 目标覆盖现有声明的四个旧版修订及 2026-07-28，逐版本验收后才能宣称支持 |
| 传输与平台 | 本轮仍为 stdio、macOS/Linux、单客户端与单活跃后端；多个监测根不代表多个后端 |
| 进程替换 | 在明确支持的恢复条件下保持客户端连接；不承诺任意业务状态无损迁移 |
| gopls 升级 | 工具与普通消息变化无需新增业务适配；协议生命周期发生变化仍可能需要更新协议适配层 |

## 设计取舍

严格内容检测会增加磁盘读取和后端重建次数。相关写入或原子替换事件即使最终内容恢复原值，也保守触发重建，以免后端保留曾观察到的中间状态；纯时间戳变化且没有内容变化，不单独要求重建。完全发生在两次观察之间、且所有事件都丢失的短暂变化不在可证明范围内。

严格结果校验也不等于副作用回滚：一个合法工具若修改被监测文件，可能已经产生效果，却因跨越刷新边界而收到 proxy 错误。方案明确报告执行不确定性，不自动重试。
